# Reflection (approximately 400 words)

Building the Lost and Found Matcher helped me understand how an AI feature can be combined with ordinary Python logic. The campus help desk problem sounds simple at first, but matching two reports is not just a matter of checking whether they mention the same object. A phone can be described by different people in different ways, and vague reports can lead to incorrect suggestions. The project therefore separates information extraction from comparison.

The LLM is used to read each report once and return structured fields: item, colour, brand, place, and a short summary. The prompt uses Authority, Exemplar, Constraint, Rubric, and Metadata so the model has a clear role, examples, allowed values, and output format. I learned that a prompt alone is not enough to guarantee a correct answer. The model can omit details or return a fact that was not actually written. For that reason, the Python program checks extracted details against the original report and has a fallback for cases where the API is unavailable.

The matching stage is kept in Python because its rules should be understandable and testable. The program rejects different item types, reports more than 30 days apart, and explicit colour or brand conflicts. It adds points for matching colour, brand, and place, then labels a candidate as likely or possible. It compares every lost report with every found report and keeps all candidates rather than showing only one result. This makes it less likely that the help desk will miss a second possible claimant.

The testing work is important because a program can run without being trustworthy. The evaluation harness checks known scoring cases, while the red-team cases examine vague reports, guessed brands, and instructions hidden inside a report. These tests help identify failure modes before the program is used with real information. The project also separates input data, source code, tests, documentation, and generated output files so the repository is easier to understand.

My most important learning is that a match score is not proof of ownership. Two people may describe similar items, and a model can make mistakes. The software should support the help desk, not replace its judgment. Before handing over an item, a staff member must ask the claimant for a detail that is not present in either report. This human checkpoint makes the process safer and fairer.

If I developed the project further, I would improve the fallback for synonyms, measure real API latency and cost, and test more edge cases. I would also seek faculty feedback before using real student reports. Overall, this project showed me that responsible AI needs clear rules, validation, testing, privacy protection, and human oversight—not just a model that produces an answer.
